# GamePilot 面试讲解边界

## 项目是什么

在自己已有的 Godot 射击游戏里建立强化学习环境，让 Python 策略调用真实游戏中的移动和射击。对照随机策略、规则策略和 PPO，记录完整回合并重放失败。目标是做可评测的自动试玩闭环，不是再写一套脱离游戏的模拟器。

目前又增加了四个版本化任务（生存、限时击杀、受伤上限、收集道具并生存）和独立的 LLM 工具调用 Agent。LLM 只可调用受限的 `step_game`，任务结果仍由环境事件和固定 grader 判定；Agent 可读取按 episode 隔离的最近动作与结果摘要，窗口大小可配置。当前测试覆盖工具参数、一次纠错、短期记忆、Ollama/OpenAI 兼容协议和错误分类；真实模型 benchmark 尚未执行，不应声称 LLM 胜过规则策略或 PPO。

## 可以具体讲的工程工作

1. **环境接口**：把硬编码键盘输入抽成统一控制接口；用 76 维结构化状态与两个九方向动作空间连接 Gymnasium。
2. **步进与回合**：每个动作推进四个物理帧；死亡和 60 秒通关返回末状态，外部限步单独标记 truncated。reset 清理整局对象、Buff 和计时状态。
3. **奖励记账**：根据相邻动作之间发生的真实生命损失、敌人死亡与存活时间计算奖励，终止奖励只支付一次。
4. **复现与测试**：刷新和掉落采用明确种子；自动检查多次重置、TCP 分包、异常断连、进程清理，并在新 Godot 进程中重放完整成功回合。
5. **训练实验**：使用 SB3 PPO；记录初始权重、模型哈希、训练配置、验证集最佳模型与最终模型，测试集不参与模型选择。

## 容易被追问的地方

**为什么没有直接用上游示例？**

自己游戏的结算会暂停整棵场景树，键盘输入、随机数与渲染动画时序也不适合训练。上游发布版的 reset seed、info 和 terminated/truncated 还需要适配。个人贡献是接入与验证这些行为，算法仍来自 SB3。

**为什么先用结构化观测？**

游戏源码可控，能先验证控制与训练问题；如果一开始加入像素编码，就会同时引入视觉表征、算力和环境接口问题。此项目不能说成视觉 Agent。

**规则 Bot 比 PPO 好，项目是否失败？**

工程链路是否正确和策略是否学得好是两件事。规则 Bot 是强基线，能检验训练是否真的值得。若 PPO 表现差，应保留结果，分析样本量、奖励和观测，而不是删掉基线或更换测试种子。

**这个 Agent 可以自动找游戏 Bug 吗？**

当前只能留下卡住候选事件、失败轨迹与结果，需要人工确认成因。玩家死亡也可能只是策略差，不能自动当作游戏 Bug。

**可以写成大模型算法项目吗？**

不可以。这里没有大模型预训练、微调或 RLHF，也没有原创 PPO。更准确的方向是游戏 AI、强化学习工程、自动试玩与测试工具。

**LLM Agent 做了什么，如何防止模型伪造通关？**

模型通过受限工具提交移动方向、射击方向和有限重复次数。Python runner 检查参数并控制真实 Godot 进程；每一步都调用同一套 task grader。模型文本不参与成绩计算。服务错误、无效参数、请求/Token 预算耗尽与游戏失败分开记录。首版观测来自结构化游戏状态，不是视觉 Agent；目前真实模型 benchmark 尚未执行。

## 下一步何时值得做

先补充独立训练种子，再考虑用规则 Bot 生成专家轨迹做行为克隆，比较“随机初始化 PPO”和“模仿学习后 PPO”的样本效率。只有真实对照支持时才写性能提升。当前第一轮只有一个训练种子，不能宣称泛化能力或稳定超过规则策略。
